# LingAI FastAPI Service — 问题清单与联调优化方向

> 基于 2026-02-11 全量代码分析，记录当前系统存在的问题及后续联调优化方向。

---

## 一、现有问题

### 🔴 P0 — 安全问题

#### 1. Redis 密码硬编码在源码中

**涉及文件**：
- [redis_cache.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/services/redis_cache.py) — `__init__` 和 `get_instance` 方法的默认参数
- [config.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/config.py) — `redis_url` 字段默认值

**问题**：Redis 连接 URL（含密码）作为函数默认参数写死在源码中，提交到 Git 后存在泄露风险。

**建议**：所有 Redis URL 仅从 `.env` / 环境变量读取，源码默认值改为 `"redis://localhost:6379/0"`（无密码本地开发地址），同时检查 Git 历史是否需要清理。

### 🟡 P1 — 架构设计问题

#### 2. Redis 两套封装并存（sync + async）

**涉及文件**：
- [redis_service.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/services/redis_service.py) — 异步版（`redis.asyncio`），用于 TTS 音频缓存
- [redis_cache.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/services/redis_cache.py) — 同步版（`redis`），用于 LLM 查询结果缓存

**问题**：
- 两套独立的连接池，资源浪费
- 连接管理方式不统一（一个全局单例模式、一个类单例模式）
- `redis_cache.py` 未从 `config.py` 读取配置，URL 硬编码在默认参数中

**建议**：统一为一套异步 Redis 封装，在 `lifespan` 中初始化，通过依赖注入使用。

#### 3. 服务实例每次请求重新创建

**涉及文件**：
- [dict_ai.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/dict_ai.py) — 每次请求 `new LLMService(settings)`
- [tts.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/tts.py) — 每次请求 `new AliyunTTSService(settings)`
- [spirit.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/spirit.py) — 每次请求 `new LLMService(settings)`

**问题**：`LLMService` 内部创建了 `AsyncOpenAI` 客户端（含连接池），每次请求重建导致连接池无法复用。

**建议**：在 `lifespan` 中初始化服务单例，通过 FastAPI 依赖注入 (`Depends`) 传递给路由处理函数。

#### 4. Pydantic 模型定义分散

**涉及文件**：
- [schemas.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/models/schemas.py) — 通用模型（`WordEntry`, `Quiz`, `DailyTask` 等）
- [dict_ai.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/dict_ai.py) — 词典相关模型（`DictAIResponse`, `DictSearchResponse` 等 9 个类）
- [content.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/content.py) — `WordEntry`（与 schemas.py 中重复定义）、`LessonContent`
- [tts.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/tts.py) — `TTSRequest`, `TTSResponse`
- [stats.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/stats.py) — `StatEvent`, `BatchStatsRequest`
- [spirit.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/routers/spirit.py) — `ChatMessage`, `SpiritChatRequest`

**问题**：模型散落在各路由文件中，存在重复定义（`WordEntry` 在 `schemas.py` 和 `content.py` 中各有一份），不利于跨模块复用和 API 文档统一。

**建议**：按业务域拆分模型文件，如 `models/dict.py`、`models/content.py`、`models/tts.py` 等，路由只引用不定义。

### 🟡 P1 — 功能实现问题

#### ✅ ~~5. 阿里云 TTS API 未实现~~（CR-P4-003 已完成）

**已处理**：
- `AliyunTTSService` 已实现阿里云 NLS Token 获取与 REST 合成调用（不再停留在 TODO）；
- 新增 `tts_provider` / `tts_fallback_enabled` / `aliyun_voice_ko` / `aliyun_voice_zh` 配置；
- `tts.py` 三个接口增加 `X-TTS-Provider` 响应头，便于联调判定主/降级链路；
- 保留 Edge TTS 作为降级能力（`TTS_PROVIDER=edge` 可显式启用）。

**联调验收（Phase4）**：
- FastAPI 直连 `GET /api/tts/play?lang=ko` 返回 `audio/mpeg`，且 `X-TTS-Provider=aliyun`；
- 网关 `GET /api/app/biz/api/tts/play?lang=ko` 返回 `audio/mpeg`，与直连字节一致；
- `TTS_PROVIDER=edge` 单次探针返回 `provider=edge`，降级链路可用。

**状态**：`CR-P4-003` 已关闭（详见项目级记录 `docs/联调测试记录-phase4.md`）。

### 🟡 P2 — 联调兼容性问题

#### 7. CORS 配置过于宽松

**涉及文件**：[main.py](file:///Users/mars/sourceCode/LingAI-Project/lingai-fastapi-service/app/main.py) — `allow_origins=["*"]`

**问题**：开发阶段可以，但部署到测试/生产环境前需要收紧，仅允许 Unified Service 的内网来源。

**建议**：根据环境变量区分，生产环境移除 CORS 或限定白名单（本服务理论上仅内网调用，可以不需要 CORS）。

#### ✅ ~~8. 缺少统一错误处理中间件~~（CR-P0-005 已完成）

**已处理**：
- `main.py` 新增全局异常处理：
  - `@app.exception_handler(HTTPException)`
  - `@app.exception_handler(Exception)`
- FastAPI 未捕获异常不再返回纯文本，统一返回 JSON，且包含 `traceId` 字段（便于 Unified 侧链路定位）。

**联调验收（Phase3）**：
- 超大时间戳触发异常时，`POST /api/stats/batch` 返回：`{"detail":"Internal Server Error","traceId":"..."}`。
- 网关侧可稳定接收 JSON 错误并输出统一错误响应。

**状态**：`CR-P0-005` 已关闭（本项）。

#### ✅ ~~9. API 响应格式不统一~~（CR-P0-005 已完成）

**已处理/已确认**：
- 已冻结契约为“方案 A”：FastAPI 返回业务数据，Unified Service 统一包装为 `code/message/data/timestamp/traceId`。
- FastAPI 保持业务域响应语义，网关负责统一外部协议，避免双层包装。

**联调验收（Phase3）**：
- `GET /api/content/levels`（直连）返回业务对象；经网关返回统一包装结构，链路一致。

**状态**：`CR-P0-005` 已关闭（本项）。
